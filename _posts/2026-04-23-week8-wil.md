이번 주에는 `CSAPP 11장`을 중심으로 네트워크 프로그래밍의 기본 흐름을 공부하고, 그 위에서 `Tiny` 웹 서버와 `Proxy Lab`이 어떤 식으로 이어지는지를 계속 정리했다. 이전까지는 포인터, 연결 리스트, 저장 엔진처럼 메모리와 파일 구조를 안쪽에서 이해하는 흐름이 강했다면, 이번 주에는 그 감각을 네트워크 바깥으로 확장하는 쪽으로 방향이 바뀌었다. 특히 인상적이었던 점은, 네트워크 프로그래밍이 완전히 새로운 세계처럼 보이지만 실제로는 **운영체제가 네트워크를 파일처럼 추상화해 준 덕분에 기존의 `fd`, `read/write`, 프로세스 감각이 그대로 이어진다**는 점이었다.

이번 주를 한 문장으로 정리하면, **"클라이언트-서버 모델과 BSD 소켓 인터페이스를 먼저 이해한 뒤, Tiny의 요청 처리 흐름과 Proxy의 중계 구조를 하나의 그림으로 연결해 보기 시작한 주"** 였다.

## 이번 주 학습 흐름

이번 주 학습은 크게 네 단계로 흘렀다. 먼저 `11.1 ~ 11.4`를 읽으면서 클라이언트-서버 모델, 네트워크를 I/O 장치로 보는 관점, IP/포트/DNS, BSD 소켓 인터페이스를 정리했다. 그 다음에는 `open_listenfd()`와 `getaddrinfo()`를 따라가며 서버 소켓이 실제로 어떻게 준비되는지 확인했다. 이어서 `tiny.c`의 `main -> doit -> parse_uri -> serve_static/serve_dynamic` 흐름을 읽으며 HTTP 요청 한 건이 어떤 함수 경계를 거쳐 처리되는지 정리했다. 마지막으로는 `proxy.c` 과제를 기준으로, 왜 프록시가 브라우저에게는 서버이고 원격 웹 서버에게는 클라이언트인지, 그리고 왜 캐시와 동시성이 뒤따라오는지를 생각했다.

이 흐름이 좋았던 이유는, 개념과 코드가 따로 놀지 않았기 때문이다. `socket`, `bind`, `listen`, `accept`를 책에서 읽고 끝내는 것이 아니라, 곧바로 Tiny 코드에서 `listenfd`와 `connfd`가 왜 분리돼 있는지로 이어졌고, `connect`의 의미도 Proxy를 볼 때 훨씬 또렷해졌다. 결국 이번 주 공부는 네트워크 이론을 외우는 쪽보다, **실제 서버 코드를 읽기 위해 필요한 최소 개념을 정확히 붙잡는 과정**에 가까웠다.

## 가장 먼저 정리된 것은 클라이언트와 서버가 "컴퓨터"가 아니라 "역할"이라는 점이었다

이번 주 초반에 가장 먼저 다시 정리된 것은, 클라이언트와 서버를 물리적인 장비 이름처럼 생각하면 오히려 흐름이 잘 안 보인다는 점이었다. `client`는 서비스를 요청하는 프로세스이고, `server`는 자원을 관리하며 응답하는 프로세스다. 즉 둘은 서로 다른 종류의 컴퓨터가 아니라, **네트워크 안에서 어떤 역할을 수행하느냐를 가리키는 이름**이다.

이 관점이 중요했던 이유는 Proxy를 이해할 때 특히 강하게 드러난다. Tiny는 비교적 단순하다. 브라우저 요청을 받아 정적 파일을 주거나 CGI 프로그램을 실행해 응답하는 서버 역할에 집중한다. 반면 Proxy는 브라우저 쪽에서는 분명 서버처럼 보이지만, 실제로는 다시 원격 웹 서버로 연결을 열고 요청을 보내야 하므로 동시에 클라이언트이기도 하다. 처음에는 이 점이 약간 헷갈렸는데, 역할 기준으로 생각하니 훨씬 명확해졌다. **한 프로그램 안에 서버 흐름(`accept`)과 클라이언트 흐름(`connect`)이 함께 들어갈 수 있다**는 사실이 바로 프록시 과제의 핵심이었다.

## 네트워크를 I/O 장치처럼 본다는 관점이 예상보다 중요했다

`11.2`를 보면서 가장 크게 남은 문장은, 호스트에게 네트워크는 하나의 `I/O device`처럼 보인다는 설명이었다. 처음 네트워크 프로그래밍을 접하면 패킷, 라우터, 케이블 같은 바깥 구조가 더 중요해 보이기 쉽다. 그런데 실제 구현 단계에서 애플리케이션이 직접 다루는 것은 그런 물리 계층이 아니라, 운영체제가 제공하는 **소켓 인터페이스와 파일 디스크립터 추상화**였다.

이 관점을 잡고 나니 Tiny나 Proxy의 코드가 훨씬 덜 낯설어졌다. 소켓도 결국 `fd`이고, `read`, `write`, `close` 같은 사고방식으로 다뤄진다. 물론 실제로는 NIC, 커널 버퍼, TCP/IP 스택이 뒤에서 움직이지만, 과제 수준에서 중요한 것은 "이 연결이 문자열이 오가는 파일 같은 통로로 보인다"는 감각이었다. 이번 주에 이 점이 정리되면서, 네트워크 코드를 완전히 새로운 문법으로 받아들이기보다 **기존 유닉스 I/O 모델의 연장선으로 읽는 습관**이 조금 생겼다.

## IP, DNS, Port를 구분해서 보는 감각이 생겼다

네트워크를 처음 공부할 때 자주 섞이는 개념이 `도메인`, `IP`, `Port`인데, 이번 주에는 이 셋의 역할을 최소한 과제 수준에서 분리해서 볼 수 있게 된 것이 꽤 중요했다. `DNS`는 이름을 주소로 바꾸는 계층이고, `IP`는 어느 호스트인지를 식별하며, `Port`는 그 호스트 안의 어느 서비스인지를 가리킨다. 즉 브라우저가 URL을 입력해 서버와 통신하려면, 결국은 "어느 호스트의 어느 프로세스와 연결할 것인가"라는 질문으로 환원된다.

이 차이는 `open_clientfd(host, port)`나 `open_listenfd(port)`를 볼 때 특히 잘 드러났다. 서버는 주어진 포트에서 연결을 받을 준비를 해야 하므로 `bind`와 `listen`이 필요하고, 클라이언트는 주어진 호스트와 포트로 연결을 열어야 하므로 `connect`가 필요하다. 여기에 `getaddrinfo()`가 들어오면, 사람이 읽는 이름과 프로그램이 쓰는 주소 정보 사이를 이어주는 다리 역할이 더 명확해진다.

특히 좋았던 점은, 이 개념들이 책 안에서만 끝나지 않고 Tiny/Proxy 흐름에 바로 연결된다는 점이었다. Tiny에서는 서버가 특정 포트에서 요청을 기다리고, Proxy에서는 요청 URI를 파싱해 `host`, `port`, `path`를 분리한 뒤 원격 서버에 다시 연결해야 한다. 개념이 코드로 떨어지는 지점이 분명해서 기억에도 더 오래 남았다.

## `socket -> bind/listen/accept`와 `socket -> connect`의 차이가 또렷해졌다

이번 주 공부에서 핵심으로 남은 것은 결국 BSD 소켓 인터페이스였다. 처음 보면 함수 이름이 비슷비슷해서 흐름이 잘 안 보이는데, 서버와 클라이언트 경로를 분리해서 보니 훨씬 이해가 쉬웠다.

서버 쪽은 대략 이렇게 흘러간다.

```text
socket
  -> bind
  -> listen
  -> accept
  -> read/write
  -> close
```

반면 클라이언트는 다음 흐름에 가깝다.

```text
socket
  -> connect
  -> read/write
  -> close
```

여기서 가장 중요하게 느껴진 것은 `listenfd`와 `connfd`를 분리해서 생각해야 한다는 점이었다. `listenfd`는 말 그대로 새 연결 요청을 기다리는 대표 창구이고, `accept`가 반환하는 `connfd`가 실제 데이터 송수신을 담당한다. 처음에는 둘 다 소켓 파일 디스크립터라서 그냥 비슷한 변수처럼 보일 수 있는데, 실제 역할은 완전히 다르다. Tiny가 반복형 서버로 동작할 수 있는 것도 `listenfd`는 계속 살아 있고, 각 요청은 새 `connfd`에서 처리된다는 구조 덕분이다.

이 차이가 명확해지니 Proxy도 더 이해하기 쉬워졌다. 프록시는 먼저 브라우저에게서 `accept`로 연결을 받고, 그 다음 원격 서버에게 `connect`로 새로운 연결을 연다. 결국 하나의 요청을 처리하기 위해 **두 종류의 소켓 역할을 한 프로그램 안에서 모두 수행하는 셈**이다.

## `open_listenfd()`를 보면서 래퍼 함수가 왜 중요한지도 보였다

이번 주에는 `open_listenfd()`를 따로 정리해 본 것도 의미 있었다. 처음에는 그냥 "서버 소켓 열어주는 편한 함수" 정도로만 생각했는데, 내부 흐름을 따라가 보니 `getaddrinfo -> socket -> setsockopt -> bind -> listen`이라는 꽤 많은 단계를 안전하게 묶어 둔 래퍼였다. 이런 래퍼가 있기 때문에 초반에는 복잡한 주소 구조체나 에러 처리를 전부 한꺼번에 붙잡지 않고, 우선 전체 서버 흐름을 이해하는 데 집중할 수 있다.

특히 `getaddrinfo()`가 `addrinfo` 연결 리스트를 돌려주고, 그 후보들을 하나씩 시도하다가 성공하는 소켓을 선택한다는 구조는 꽤 인상적이었다. 예전에는 네트워크 주소를 그냥 숫자 몇 개 정도로 막연히 생각했는데, 실제로는 주소 체계, 소켓 타입, 프로토콜, 주소 길이 같은 정보가 모두 구조체로 묶여 있고, 서버 함수는 그 후보들을 순회하면서 가장 적절한 바인딩을 찾는다. 이 부분은 아직 완전히 손에 익은 건 아니지만, 적어도 이제는 `open_listenfd()`를 마법처럼 보지 않고 **서버 초기화 절차를 감춘 추상화**로 볼 수 있게 됐다.

## Tiny 웹 서버는 HTTP 요청 한 건을 함수 단위로 읽기 좋게 쪼개 둔 코드였다

이번 주에 실제 코드로 가장 많이 본 것은 `tiny.c`였다. Tiny의 좋은 점은 전체 흐름이 꽤 직선적이라는 데 있다. `main`은 포트를 열고 연결을 받고, `doit`는 HTTP 요청 한 건을 처리하며, 그 안에서 요청라인을 읽고 메서드를 확인하고 헤더를 소비하고 URI를 해석한 뒤 정적/동적 컨텐츠로 분기한다.

이 흐름을 따라가면서 특히 좋았던 점은, HTTP 서버가 처음부터 거대한 프레임워크처럼 느껴지지 않았다는 것이다. 결국 최소 서버는 아래 질문들에 답하면 된다.

- 요청라인에서 `method`, `uri`, `version`을 어떻게 뽑을 것인가
- 이 요청이 정적 파일 요청인지 CGI 실행 요청인지 어떻게 구분할 것인가
- 요청한 파일이 실제로 존재하고 읽기 또는 실행 권한이 있는지 어떻게 검사할 것인가
- 응답 헤더와 본문은 어떤 순서로 써야 하는가

이걸 함수 단위로 다시 보면 `read_requesthdrs`, `parse_uri`, `serve_static`, `serve_dynamic`, `clienterror` 같은 작은 단위로 나뉜다. 이 분해가 특히 좋았던 이유는, 네트워크 과제가 아니라도 결국 좋은 시스템 코드는 **입력, 판정, 권한 검사, 분기, 출력**을 명확한 경계로 쪼개는 편이 읽기 쉽다는 점을 다시 느끼게 해줬기 때문이다.

## 정적 컨텐츠와 동적 컨텐츠가 왜 처리 방식부터 다른지도 이해됐다

Tiny를 보면서 의외로 인상적이었던 부분은, 정적 파일과 동적 컨텐츠를 단순히 "둘 다 웹페이지"로 보면 흐름이 잘 안 보인다는 점이었다. 정적 컨텐츠는 결국 서버 파일 시스템에 있는 파일을 읽어 응답하면 되므로, 파일 타입을 결정하고 길이를 계산한 뒤 바이트를 보내면 된다. 반면 동적 컨텐츠는 서버가 결과 파일을 그냥 들고 있는 것이 아니라, **별도 프로그램을 실행해서 그 프로그램의 표준출력을 응답으로 사용해야 한다**.

그래서 `serve_dynamic`에서는 `fork`, `execve`, `dup2` 같은 프로세스/파일 디스크립터 조작이 등장한다. 이 부분을 보고 나니 예전에 따로 공부했던 프로세스 개념이 여기서 연결되는 느낌이 있었다. CGI 프로그램은 그냥 "백엔드 로직"이 아니라, **실행 결과를 HTTP 본문 형태로 표준출력에 써 주는 독립 프로세스**였다. 결국 웹 서버 구현은 네트워크만의 문제가 아니라, 파일 I/O, 프로세스 생성, 환경변수 전달, 표준출력 리다이렉션이 전부 한 군데서 만나는 문제라는 걸 다시 느꼈다.

## Proxy Lab은 서버를 만드는 과제이면서 동시에 중간 계층을 설계하는 과제처럼 보였다

Tiny를 이해하고 나서 Proxy를 보기 시작하니, 이 과제가 단순히 "웹 서버 하나 더 구현하기"는 아니라는 점이 더 분명해졌다. Proxy는 요청을 직접 처리하는 대신, 브라우저가 보낸 요청을 읽고, URI에서 `host`, `port`, `path`를 추출하고, 원격 서버에 새 요청을 만들어 보내고, 다시 응답을 받아 브라우저에 전달해야 한다. 즉 핵심은 컨텐츠를 직접 제공하는 것이 아니라 **요청과 응답을 안전하게 중계하는 것**이다.

여기서 특히 중요해 보인 것은 "브라우저가 준 요청을 그대로 넘기지 않고 프록시 규칙에 맞는 새 요청으로 정리해야 한다"는 점이었다. `Host`, `User-Agent`, `Connection`, `Proxy-Connection` 같은 헤더를 명시적으로 다뤄야 한다는 부분도 이 맥락에서 이해됐다. 결국 프록시는 단순 복사기가 아니라, HTTP 메시지를 읽고 필요한 형태로 재구성하는 중간 계층이다.

또 한 가지 흥미로웠던 점은, Proxy를 공부하면 `CDN`이나 캐시 서버 개념도 훨씬 구체적으로 느껴진다는 것이다. 아직 캐시를 본격 구현한 단계는 아니지만, 같은 URI 요청이 반복될 때 응답 바이트를 저장해 두고 재사용한다는 아이디어는 "중간 계층에서 응답을 대신 제공한다"는 큰 그림으로 자연스럽게 이어진다.

## 이번 주에는 동시성과 캐시가 왜 바로 따라오는지도 미리 보였다

Proxy Lab의 목표가 순차 처리에서 끝나지 않고 동시성과 캐시까지 가는 이유도 이번 주에 어느 정도 납득됐다. 순차 프록시는 한 요청을 처리하는 동안 다른 요청을 기다리게 만든다. 브라우저 입장에서는 아주 답답한 서버가 된다. 그래서 연결마다 스레드를 하나 두거나 다른 동시성 모델을 도입해야 한다. 여기까지는 비교적 자연스럽다.

그런데 캐시가 들어오면 상황이 달라진다. 이제 여러 스레드가 같은 캐시 자료구조를 동시에 읽고 쓰게 될 수 있고, 캐시 크기 제한과 교체 정책까지 같이 고민해야 한다. 즉 프록시는 단순 소켓 프로그래밍 과제가 아니라, **네트워크 I/O 위에 동기화와 메모리 정책까지 얹히는 시스템 과제**로 확장된다. 이번 주에는 아직 구현을 끝낸 단계는 아니지만, 최소한 왜 이 과제가 뒤로 갈수록 어려워지는지는 훨씬 잘 보였다.

## 이번 주에는 네트워크 공부가 팀 프로젝트 구조를 다시 설명하는 일로도 자연스럽게 이어졌다

이번 주가 특히 의미 있었던 이유는, `CSAPP 11장` 내용을 책에서만 읽고 끝내지 않았기 때문이다. 이번 주 후반에 팀 프로젝트 README를 손보는 커밋들을 다시 정리해 보니, 실제로도 이번 주 학습이 서버 구조를 다시 이해하는 데 곧바로 이어져 있었다. `README 다이어그램에 스레드 풀 구조 반영`, `README에 서버 설정 기본값 주석 추가`, `README에 DB 락 범위 개선 과정 추가` 같은 작업은 겉으로 보면 문서 수정처럼 보이지만, 실제로는 **요청 한 건이 어떤 경계를 지나고, 병목이 어느 지점에서 생기며, 동시성이 어디서 깨지는지를 다시 설명하는 작업**에 더 가까웠다.

예전에는 서버를 설명할 때 `HTTP 서버`라고 한 덩어리로 묶어 말해도 큰 문제는 없다고 느꼈다. 그런데 이번 주에 Tiny와 Proxy 흐름을 따라간 뒤에는, 그 표현이 실제 실행 경로를 너무 많이 감춘다는 점이 더 잘 보였다. `accept`를 담당하는 메인 루프와, 대기 중인 연결을 큐에 넣는 단계, 그리고 worker thread가 실제로 요청을 읽고 응답을 보내는 단계는 서로 다른 책임을 가진다. 그래서 README 다이어그램도 `server.c`의 `accept loop`, `thread_pool.c`의 `Job Queue`, `Worker Threads`로 분리해 다시 그리게 됐다. 이 작업을 하면서 네트워크 서버를 이해한다는 것은 결국 "소켓을 연다" 수준에서 멈추는 것이 아니라, **어느 스레드가 언제 연결을 받고, 누가 그 연결을 실제로 처리하며, 그 사이에 어떤 버퍼링 계층이 끼어 있는지까지 분리해서 보는 일**이라는 점이 더 분명해졌다.

## `accept loop`와 worker를 분리해서 보니 서버 설정값도 의미가 생겼다

이번 주 커밋 중 하나는 `worker_count`, `queue_capacity`, `backlog` 기본값에 주석을 달아 둔 수정이었다. 처음 보면 아주 작은 문서 정리처럼 보일 수 있다. 그런데 이 숫자들을 다시 뜯어보면, 사실은 서로 다른 병목 지점을 각각 가리키고 있다. `backlog`는 커널이 아직 `accept`되지 않은 연결을 얼마나 대기시킬 수 있는지와 관련 있고, `queue_capacity`는 이미 받아온 `client fd`를 애플리케이션 레벨에서 얼마나 버퍼링할지와 연결되며, `worker_count`는 그 대기열을 실제로 얼마나 병렬 처리할지를 결정한다.

이 구분은 Tiny를 공부하면서 본 `listenfd`와 `connfd`의 차이, 그리고 Proxy에서 한 요청이 두 방향 소켓 역할을 모두 수행한다는 점과도 자연스럽게 이어졌다. 결국 네트워크 프로그램에서 "서버가 바쁘다"는 말은 하나의 상태로 뭉뚱그릴 수 있는 표현이 아니었다. **커널 대기열이 찬 것인지, 애플리케이션 큐가 밀린 것인지, worker가 부족한 것인지, 혹은 worker는 충분하지만 내부 공유 자원에서 막히는 것인지**를 나눠서 봐야 했다. 이번 주에는 이 감각이 조금 생겼고, 그래서 설정값도 이제는 막연한 튜닝 숫자가 아니라 구조를 설명하는 단서처럼 보이기 시작했다.

## 동시성에서는 lock을 얼마나 오래 잡느냐가 결국 병렬성의 품질을 결정했다

이번 주 후반에 가장 인상적이었던 프로젝트 쪽 학습은 `DB lock` 범위를 줄인 과정을 README에 정리한 일이었다. 처음에는 요청 처리 전체를 하나의 lock으로 감싸면 가장 안전하다고 생각하기 쉽다. 실제로 구현 초반에는 그렇게 넓게 잡는 편이 마음이 놓이기도 한다. 하지만 이 방식은 SQL 파싱, 에러 응답 생성, JSON 직렬화처럼 실제 공유 데이터와 직접 관계없는 작업까지 한꺼번에 직렬화해 버린다. worker thread가 여러 개 있더라도, 결국 중요한 구간이 너무 넓게 잠겨 있으면 병렬성은 거의 사라진다.

그래서 지금 구조에서는 lock을 요청 전체가 아니라 **실제 `Table` 접근 구간** 안으로 밀어 넣고, 더 나아가 `TABLE_BUCKET_COUNT = 16` 기준 bucket별 `pthread_rwlock_t`로 나눠 보호한다. 이 변화는 단순한 최적화라기보다, Proxy Lab을 보며 미리 느꼈던 "동시성은 결국 공유 자원을 어떤 단위로 나누느냐의 문제"라는 감각과 정확히 닿아 있었다. 한 요청이 `bucket[3]`에 쓰는 동안 다른 요청이 `bucket[7]`을 읽을 수 있다면, 이제 동시성은 단순히 스레드 개수를 늘리는 문제가 아니라 **데이터 구조와 lock 경계가 병렬 실행을 얼마나 허용하도록 설계돼 있는가**의 문제가 된다.

이 부분은 앞으로 Proxy 캐시를 구현할 때도 그대로 이어질 것 같다. 스레드를 붙이는 것 자체보다 더 중요한 것은, 어떤 자료구조를 공유하고 그 공유 범위를 어디까지 잠글지 결정하는 일이다. 이번 주에는 네트워크 공부를 하면서도 결국 다시 lock과 병렬성 문제로 돌아오게 됐는데, 오히려 그 덕분에 네트워크 프로그래밍이 독립된 주제가 아니라 **운영체제의 I/O, 스레드, 동기화 감각이 한꺼번에 만나는 영역**이라는 점을 더 분명하게 느꼈다.

## 이번 주를 돌아보며

이번 주 공부는 네트워크 용어를 많이 외운 주라기보다, **네트워크 프로그램을 어떤 추상화로 읽어야 하는지 처음 감을 잡은 주**에 더 가까웠다. 클라이언트와 서버는 컴퓨터 종류가 아니라 역할이라는 점, 네트워크는 애플리케이션 입장에서 I/O 장치처럼 보인다는 점, 소켓도 결국 `fd`라는 점, 서버는 `listen/accept`, 클라이언트는 `connect` 흐름으로 읽으면 된다는 점이 이번 주에 하나의 그림으로 조금씩 붙기 시작했다. 그리고 이 감각이 책 안에 머문 것이 아니라, 실제 팀 프로젝트에서 `accept loop`, job queue, worker thread, bucket lock 구조를 다시 설명하는 데까지 이어졌다는 점이 특히 의미 있었다.

또 Tiny와 Proxy를 함께 보면서, 네트워크 프로그래밍은 단순히 요청 문자열을 주고받는 문제가 아니라는 점도 더 분명해졌다. 파일 권한 검사, MIME 타입 판정, 프로세스 생성, CGI 실행, 요청 재작성, 캐시, 동기화처럼 여러 운영체제 개념이 한 과제 안에서 이어진다. 그래서 이번 주는 "웹 서버를 공부했다"기보다, **운영체제에서 배운 파일, 프로세스, 디스크립터 감각이 네트워크 코드로 확장되는 과정을 처음 제대로 본 주**였다고 정리하는 편이 더 맞는 것 같다.

다음에는 여기서 한 걸음 더 나아가, Tiny를 완전히 마무리한 뒤 Proxy의 순차 처리 버전을 실제로 안정화하고, 그 위에 스레드 기반 동시성과 캐시 정책까지 붙여보면서 네트워크 프로그램이 왜 곧 시스템 프로그램인지 더 분명하게 확인해보고 싶다.
