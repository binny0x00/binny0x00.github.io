이번 주는 `C` 문법 자체를 익히는 시간이라기보다, **디스크 위에서 돌아가는 저장 엔진을 어떤 경계로 나누고 어떤 자료구조로 설명할 것인가**를 계속 붙들고 있던 한 주였다. 이전 주차까지는 구조체, 포인터, 연결 리스트, allocator처럼 메모리 안에서의 구조를 이해하는 흐름이 강했다면, 이번 주에는 그 감각을 파일 페이지와 인덱스 구조로 밀어 넣는 쪽으로 방향이 확실히 바뀌었다. 문자열로 들어온 SQL이 결국 어떤 페이지를 읽고 어떤 바이트를 갱신하는지까지 내려가서 생각해야 했기 때문에, 체감상 훨씬 더 시스템 과제에 가까웠다.

이번 주를 한 문장으로 정리하면, **"문서로 아키텍처를 먼저 고정한 뒤, `pager + slotted heap + B+ tree + 디버그/성능 계측`으로 이어지는 최소 SQL 엔진을 실제 구현 흐름으로 연결해 본 주"** 였다.

## 이번 주 학습 흐름

처음에 팀에서 합의한 방향은 **SQL breadth보다 storage depth에 집중하자**는 것이었다. `JOIN`, `UPDATE`, 복잡한 문법을 넓게 넣는 대신, `INSERT`, `SELECT`, `DELETE` 같은 최소 문법 위에 실제 디스크 저장 구조를 얹는 쪽으로 범위를 정리했다. 이 합의를 먼저 문서로 고정하고 나서 구현에 들어갔다는 점이 이번 주를 이전 주차들과 다르게 만들었다.

구현 흐름은 구조를 먼저 정의하고, 설명 가능성을 함께 올리는 방향으로 이어졌다. `pread`/`pwrite` 기반 pager를 두고, row는 heap page에 저장하고, `id -> row_ref`는 B+ tree leaf에 두는 식으로 계층을 나눴다. 실행기와 저장 계층을 정리한 뒤에는 페이지 구조와 함수 역할을 소스/헤더 주석과 README, 발표 문서로 다시 풀어냈다. 후반에는 `.log`, `.flush`, `.debug` 같은 메타 명령어와 대량 데이터 생성기, 성능 테스트 가이드까지 붙으면서, 이 프로젝트는 단순한 "작동하는 코드"에서 **동작 이유를 설명하고 수치로 비교할 수 있는 코드** 쪽으로 이동했다.

이 흐름이 특히 의미 있었던 이유는, 기능을 아무 순서 없이 덧붙인 주가 아니었기 때문이다. 오히려 **설계 문서로 경계를 고정하고, 구현하고, 다시 문서와 계측 도구로 설명력을 높이는 사이클**을 빠르게 여러 번 돌린 주에 가까웠다. 시스템 구현에서는 코드만 있는 상태보다 "왜 이렇게 나눴는지"를 끝까지 설명할 수 있는 상태가 훨씬 중요하다는 걸 이번 주에 더 강하게 느꼈다.

## 가장 크게 배운 점은 pager가 곧 DB의 메모리 관리자라는 것

이번 주에 가장 크게 남은 개념은 `pager`였다. 처음에는 그냥 파일 입출력을 담당하는 유틸리티 계층처럼 보였지만, 구현을 따라갈수록 pager는 사실상 **DB 안의 메모리 관리자**에 더 가까웠다. 페이지를 읽어와 프레임 캐시에 올리고, dirty 상태를 추적하고, 필요하면 flush하고, 더 이상 쓰지 않는 페이지는 free list로 재사용한다. 이 흐름은 이름만 다를 뿐 allocator에서 free block을 관리하던 감각과 꽤 비슷했다.

특히 신경 썼던 부분은, row 단위가 아니라 **page 단위 사고**로 옮겨가야 한다는 점이었다. `malloc` 과제에서는 free block을 어떻게 찾고 병합할지 고민했다면, 이번 주에는 어떤 페이지를 메모리에 올려둘지, 언제 디스크에 다시 쓸지, 빈 페이지를 어떻게 재사용할지를 고민하게 됐다. `pager_alloc_page()`와 free page list를 보면서는 allocator에서 보던 free list가 거의 그대로 다른 층위로 옮겨온 느낌도 강했다.

이 지점에서 특히 인상적이었던 건, 페이지가 단순한 저장 단위가 아니라 **설명 가능한 시스템 경계**라는 점이었다. parser는 문장을 읽고, planner는 접근 경로를 정하고, executor는 실행 흐름을 선택하지만, 실제로 데이터를 읽고 쓰는 순간에는 결국 pager가 중심에 서게 된다. 즉 SQL 엔진을 만든다고 했을 때, 핵심은 문법 자체보다도 어떤 페이지를 어떤 순서로 접근하게 만들 것인가에 훨씬 더 가까웠다.

## B+ tree를 구현한다는 건 자료구조를 디스크 관점으로 다시 배우는 일이었다

이번 주에는 B+ tree를 단순히 "탐색이 빠른 트리"로 이해하는 수준에서 한 단계 더 내려갔다. 메모리 안의 포인터 기반 트리가 아니라, **노드 하나가 곧 파일의 페이지 하나**라는 전제를 놓고 다시 보게 됐기 때문이다. 자식을 가리키는 것도 포인터가 아니라 page id이고, leaf에는 row 전체가 아니라 `key + row_ref`만 둔다. 이렇게 되면 트리는 단순한 추상 자료구조가 아니라, 디스크 접근 횟수를 줄이기 위한 형태로 읽히기 시작한다.

이 관점 전환이 가장 선명하게 드러나는 부분은 `INDEX_LOOKUP`과 `TABLE_SCAN`의 차이였다. 100만 건 이상 데이터 기준으로, `WHERE id = ?`는 root에서 leaf를 거쳐 heap row를 찾는 데 몇 페이지 안쪽으로 끝나지만, 인덱스가 없는 칼럼 검색은 힙 페이지를 거의 끝까지 순회해야 한다. 결국 B+ tree의 핵심은 "이론상 로그 시간"이라는 표현보다, **같은 1건을 찾기 위해 몇 페이지를 읽느냐**로 이해하는 편이 훨씬 정확하다는 걸 이번 주에 제대로 체감했다.

이 과정에서 planner의 의미도 전보다 더 분명해졌다. 예전에는 parser 다음에 planner가 왜 한 단계 더 필요한지 다소 추상적으로 느껴졌는데, 이번에는 `WHERE id = ?`일 때 `INDEX_LOOKUP`을 고르고, 그렇지 않으면 `TABLE_SCAN`을 선택하는 구조를 직접 짜보면서 planner가 실제 I/O 경로를 바꾸는 계층이라는 점이 또렷해졌다. 즉 planner는 단순한 중간 단계가 아니라, "이 쿼리를 어떤 비용 모델로 실행할 것인가"를 정하는 자리였다.

## 이번 주 후반에는 설명 가능한 구현을 만드는 일이 더 중요해졌다

구현이 어느 정도 자리를 잡은 뒤부터는, 기능 추가 못지않게 문서와 주석이 큰 비중을 차지했다. README에 실행 흐름과 로직 설명이 대폭 보강됐고, 소스와 헤더 전반에 한글 주석이 붙었으며, 페이지 레이아웃과 프레임 캐시, 데이터 검색 흐름을 다이어그램과 발표 자료로 다시 정리했다. 처음에는 문서 작업 비중이 큰 것이 약간 우회처럼 느껴질 수도 있었지만, 실제로는 그 반대였다. **설명할 수 없는 저장 구조는 결국 제대로 이해한 구현이라고 보기 어렵다**는 걸 팀 전체가 의식하고 있었다.

개인적으로 이 대목이 이번 주를 가장 잘 보여준다고 느꼈다. 코드가 돌아가는 것만 보면 일단 기능은 완성처럼 보일 수 있지만, B+ tree split이나 heap page layout, dirty flush 타이밍 같은 부분은 구현자도 다시 설명하려고 하면 금방 흐려질 수 있다. 그래서 코드에 주석을 붙이고 별도 문서로 ASCII 레이아웃과 바이트 계산을 정리하는 작업이 단순 부가 작업이 아니라, **복잡한 시스템을 스스로 다시 이해하는 과정**이었다.

## 디버그 모드와 성능 테스트 도구가 붙으면서 프로젝트가 살아났다

`.log`, `.flush`, `.debug`, `gen_data`를 붙이면서 이 프로젝트는 한 단계 더 실제적인 상태로 넘어갔다. dirty 페이지가 high watermark 이상 쌓이면 low watermark까지 선제 flush하는 로직은 단순한 편의 기능이 아니라, 캐시와 디스크 동기화 시점을 어떻게 다룰지에 대한 선택이었다. 이 부분을 짜면서 "쓰기 성능"과 "안전하게 디스크에 반영하는 시점"이 분리된 고민이라는 점도 더 명확해졌다.

`.debug`가 추가된 것도 인상적이었다. 쿼리마다 소요 시간, 페이지 로드 수, 캐시 hit/miss, 디스크 기록 횟수를 보여주기 시작하면, 이제 SQL 실행은 눈에 보이지 않는 내부 동작이 아니라 수치로 설명 가능한 행동이 된다. 여기에 `gen_data`와 성능 테스트 가이드까지 붙으면서, "B+ tree가 빠르다"는 말도 단순 설명이 아니라 `INDEX_LOOKUP`과 `TABLE_SCAN`을 실제로 비교하는 데모로 바뀌었다. 시스템 구현에서는 기능이 있다는 사실보다, **왜 빠르고 왜 느린지를 관찰 가능한 형태로 드러내는 장치**가 훨씬 중요하다는 걸 여기서 가장 많이 느꼈다.

또 하나 인상적이었던 건, 성능 개선도 추상적인 최적화가 아니라 꽤 구체적인 병목에 반응했다는 점이다. 대량 더미 데이터 생성 속도를 올리기 위해 release 빌드를 분리하고, 순차 insert에서 마지막 힙 페이지 캐시를 두어 힙 체인 전체를 반복 탐색하지 않게 만든 변경은, 결국 "어디서 반복 비용이 새고 있는가"를 보고 구조를 바꾼 사례였다. 성능을 숫자로 읽고, 그 숫자를 다시 구조 수정으로 연결하는 감각을 이번 주에 얻었다.

## 이번 주를 돌아보며

이번 주는 SQL 문법을 더 많이 외운 주가 아니라, **저장 엔진을 어떤 층으로 나누고 어떤 단위로 사고해야 하는지 처음 제대로 체감한 주**였다. parser, planner, executor, storage로 계층을 나누는 이유가 단순한 설계 미학이 아니라, 쿼리 의미와 실제 I/O 경로를 분리하기 위한 선택이라는 점이 더 분명해졌다. 또 메모리에서 익혔던 연결 리스트나 allocator 감각이 페이지 캐시, free page list, B+ tree split/merge 같은 주제로 자연스럽게 이어진다는 점도 꽤 인상적이었다.

무엇보다 크게 남은 것은, 시스템 프로젝트에서는 기능 구현과 설명 가능성이 따로 가지 않는다는 점이었다. 문서, 주석, 발표 자료, 디버그 도구, 성능 테스트 가이드가 구현 코드와 거의 같은 무게로 붙어 있었는데, 처음에는 이것이 돌아가는 길처럼 보여도, 결국 복잡한 저장 구조를 자기 언어로 다시 설명할 수 있어야 다음 수정도 가능해진다. 그런 의미에서 이번 주는 "SQL 엔진을 만들었다"기보다, **디스크와 페이지, 인덱스와 계측이라는 관점으로 시스템 구현을 바라보는 법을 배우기 시작한 주**였다.

다음에는 여기서 한 걸음 더 나아가, 지금 만든 구조를 단순 데모에서 끝내지 않고 삭제 후 재사용 경로, split/merge 경계 조건, 대량 데이터에서의 캐시 정책 차이까지 더 검증해보고 싶다.
